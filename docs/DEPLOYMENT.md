# Deployment readiness

## Current status

This repository is not approved for production deployment yet. The operational system includes authentication and password recovery, inventory custody and serialized opening stock, branch transfers, hire/return and deposits/refunds, CRM/quotations with queued PDF email and custom-order/hire/sale conversion, custom production orders and accrual invoices, bulk inventory valuation and COGS, serialized hire asset capitalization/depreciation, vendor bills and payables, an Onfon SMS outbox, Daraja STK prompts/callback settlement, an immutable balanced journal, privileged-account 2FA, report CSV/PDF downloads, and encrypted local/external backup support. Local feature, browser, accessibility and build checks pass. CI now includes a PostgreSQL 16/Redis 7 migration and feature-test job, but it has not yet run on a remote CI runner. Remaining release gates include finance-reviewed historical invoice cutover, accountant-approved tax/statutory mappings, live-provider verification, provisioned S3 backup storage and isolated restore drills, real-device camera validation, staging concurrency/performance/Core Web Vitals and security evidence, production mail/queue configuration, EC2 deployment and operational monitoring. See [implementation progress](IMPLEMENTATION_PROGRESS.md).

## Target runtime

- Supported PHP 8.3+ and Composer 2; current framework baseline is Laravel 13.
- PostgreSQL with automated encrypted backups and tested point-in-time restore; Redis for cache, sessions, rate limiting and queue workers.
- Nginx or equivalent TLS terminator; HTTPS required for camera access and secure cookies.
- Node/npm only required for asset builds, not the web runtime.
- Separate worker process for queued work and scheduler every minute; process supervision, restart-on-failure and queue-age alerts required.

SQLite/file session/cache/queue settings in `.env.example` are for local setup, not a multi-user production service.

Queued password-reset and CRM reminder email use Amazon SES SMTP in production. Verify the `gownsea.com` SES identity with Easy DKIM, publish its three CNAME records in DNS, and request production sending access if the SES account is still sandboxed. Store SES SMTP credentials as runtime secrets and configure the regional SMTP endpoint, port 587, and `no-reply@gownsea.com` as the sender; SMTP credentials are distinct from AWS API access keys. Keep Zoho's MX and SPF records for inbound mail; SES DKIM provides aligned domain authentication. The CRM reminder scheduler is registered every five minutes; run Laravel's scheduler at least once per minute. `MAIL_MAILER=log` and local database queue are development defaults and do not deliver production email.

## Build and rollout checklist

1. Provision PostgreSQL, Redis, private object storage, SES domain verification and SMTP credentials, required SMS credentials and a dedicated least-privilege runtime identity.
2. Set `APP_ENV=production`, `APP_DEBUG=false`, production `APP_KEY`, trusted `APP_URL`, `APP_TIMEZONE=Africa/Nairobi`, database/Redis credentials, `SESSION_SECURE_COOKIE=true`, and explicit queue/cache/session stores. Use a secrets manager; never place production secrets in source control.
3. Build dependencies: `composer install --no-dev --prefer-dist --optimize-autoloader`, `npm ci`, `npm run build`.
4. On a release job with backups verified: `php artisan down`, `php artisan migrate --force`, `php artisan config:cache`, `php artisan route:cache`, `php artisan view:cache`, `php artisan up`.
   On an upgrade that already has receipt/refund/deposit/paid-expense data, run `php artisan gownsea:ledger-backfill --dry-run`, review the eligible counts, then run `php artisan gownsea:ledger-backfill` before enabling the ledger screen. It is chunked and idempotent; retain the pre-migration backup and reconcile the posted account balances after the backfill.
   For historical hire and completed custom-order invoices, first run `php artisan gownsea:invoice-backfill --dry-run`. Review every listed reference, customer, branch, historical invoice date and amount against the approved opening-balance schedule. Only after finance signs off, run `php artisan gownsea:invoice-backfill --confirm-reviewed`; it is idempotent and posts invoice journals with the historical issue date. Save the preview and approval with the cutover record.
5. Run the web process, queue workers and scheduler under a supervisor. Configure Laravel's `/up` health endpoint and alert on failed jobs, queue delay, database exhaustion, disk/storage pressure and backup age.
6. Create the initial named staff administrator through a secured operator session using `php artisan gownsea:create-staff-user`; assign only required locations. Remove temporary credentials and verify login/session revocation.
7. Verify HTTPS, secure cookies, CSRF, rate limits, location isolation, upload/storage policy, audit history, backups and restore in staging before customer data is loaded.

Rollback must restore a compatible code/schema pair. Do not roll back data migrations that have already accepted production writes without an explicit recovery plan.

## AWS EC2 and S3 preparation

The selected deployment target is an Ubuntu 24.04 LTS EC2 host with PostgreSQL, Redis, and private S3 backup storage. `deploy/aws/ec2/prepare-ubuntu-24.04.sh` installs the PHP 8.3 runtime, Nginx, Supervisor, Composer and PostgreSQL client tools. Run it through Systems Manager after attaching the instance profile; the host needs no inbound SSH rule or long-lived AWS access keys. Use Systems Manager Session Manager for operator access and retain HTTPS-only customer traffic.

`infra/aws/gownsea-backup-storage.yml` creates a private S3 bucket and an EC2 instance profile. It enables all S3 Block Public Access controls, bucket-owner-enforced ownership, versioning, server-side encryption, TLS-only bucket access, 90-day backup retention and lifecycle cleanup of old object versions. The EC2 role can read and write objects only under the configured backup prefix; it cannot delete objects. The bucket is retained if the CloudFormation stack is deleted. The application encrypts each backup archive before upload, and S3 adds server-side encryption. Review the bucket name and retention parameters before deploying the stack.

For the complete network and runtime baseline, `infra/aws/gownsea-production-platform.yml` creates a two-AZ VPC, public HTTPS load balancer, private two-instance application group, private encrypted PostgreSQL 16 with managed master credentials, Multi-AZ Redis with a generated authentication secret, private versioned S3 backups, and least-privilege instance access. It requires the client-selected Ubuntu 24.04 application AMI, an ACM certificate, globally unique backup bucket name, and a review of CIDR ranges and instance sizes. The template creates two NAT gateways for private subnet egress, which add ongoing infrastructure cost. It does not create DNS records, load application code, or configure GOWNSEA secrets. DNS, a prepared application image, domain, and runtime secrets must be supplied before deployment. The database master secret is for controlled operations only; create a separate restricted Laravel database user for runtime. Do not deploy this stack until the AWS account owner approves region, cost and network inputs.

Recommended recovery baseline: daily encrypted archives at 01:00 Africa/Nairobi, 90-day S3 retention, an initial **RPO of 24 hours** and **RTO of 8 hours**. Treat the RPO/RTO as operating targets and verify them with an isolated restore drill before launch; they are not proven by successful backup upload alone. Use database point-in-time recovery in addition to the application archive if the selected PostgreSQL service supports it.

Africa (Cape Town), `af-south-1`, is the recommended starting region for a Kenya workload. This region is opt-in, so enable it on the AWS account before provisioning; use another approved region by overriding `AWS_DEFAULT_REGION` if account availability, data-residency requirements or costs call for it. The production environment template is [production.env.example](../deploy/aws/ec2/production.env.example). It intentionally contains no secrets. On EC2, leave `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` unset so the AWS SDK obtains short-lived credentials from the instance role.

After the AWS account and EC2 access are supplied:

1. Deploy the S3/role stack from `infra/aws/gownsea-backup-storage.yml` in the selected region. Pass a globally unique bucket name and keep the 90-day backup lifecycle unless the business approves a different retention period. The operator command is `aws cloudformation deploy --region af-south-1 --template-file infra/aws/gownsea-backup-storage.yml --stack-name gownsea-backup-prod --capabilities CAPABILITY_IAM --parameter-overrides BackupBucketName=<globally-unique-name>`; authenticate with AWS IAM Identity Center or another temporary operator identity first.
2. Attach the stack's `GownseaEc2InstanceProfile` output to the EC2 host. Confirm Systems Manager reports the instance as managed; allow inbound 80/443 as required for the web endpoint and do not open port 22 for routine administration.
3. Prepare an Ubuntu 24.04 LTS host with an encrypted persistent EBS volume. Run `deploy/aws/ec2/prepare-ubuntu-24.04.sh` through Systems Manager. After DNS points to the host, stop Nginx, issue a certificate with `certbot certonly --standalone --agree-tos -m <operations-email> -d <gownsea-domain>`, and start Nginx. Render `deploy/aws/ec2/gownsea.nginx.conf.template` with the domain, enable the site and reload Nginx. Configure production PostgreSQL and Redis endpoints and `/var/www/gownsea/shared/.env` from the production template using a secrets manager. Complete SES identity/DKIM verification and attach the SES sending policy to the EC2 instance role before enabling queued mail.
4. Set `AWS_DEFAULT_REGION`, `AWS_BUCKET`, `GOWNSEA_BACKUP_EXTERNAL_DISK=s3`, `GOWNSEA_BACKUP_EXTERNAL_PREFIX=gownsea-backups`, a dedicated random backup encryption key, and the private local backup directory. Keep `APP_KEY` separate from the backup key.
5. Build the release artifact in CI with `composer install --no-dev --prefer-dist --optimize-autoloader && npm ci && npm run build`; copy that artifact to the EC2 host and run `deploy/aws/ec2/deploy-release.sh <built-source-directory> <release-id>` through Systems Manager. The script excludes local environment files, links shared storage, installs production dependencies, runs migrations in maintenance mode and switches the release symlink. After the first deployment, enable `gownsea-queue.service` and `gownsea-scheduler.timer` with systemd.
6. Run a backup and confirm the encrypted object appears under the S3 prefix. Restore it into an isolated staging environment and reconcile key records, payment/deposit/refund balances, private files, queue processing and login before production traffic is enabled.

The active site currently runs from `/var/www/gownsea/current` on a shared Ubuntu 26.04 EC2 host, alongside unrelated sites. The site has a shared runtime environment and `/up` health endpoint. Use the scoped release workflow in [RELEASE_PROCESS.md](RELEASE_PROCESS.md) for application deployments. Do not run the Ubuntu 24.04 host preparation script or AWS infrastructure templates against this shared production host. The dedicated Ubuntu 24.04 baseline above remains the target for any future isolated host. Never paste long-lived AWS keys into chat or commit them; prefer role-based access for EC2 and temporary identity federation for deployment operators.

## Backups and recovery (required before launch)

The application provides `gownsea:backup` and `gownsea:restore`. They create an authenticated XChaCha20-Poly1305 encrypted archive containing the database and private application files. SQLite file databases and PostgreSQL are supported; PostgreSQL runtime hosts must provide `pg_dump` and `pg_restore` executables. A dedicated encryption key of at least 32 characters is required. Keep that key in a secrets manager and store a protected recovery copy separately from the backups.

Set `GOWNSEA_BACKUP_ENCRYPTION_KEY` and `GOWNSEA_BACKUP_DIRECTORY` before running `php artisan gownsea:backup`. The scheduler creates a daily backup at 01:00 Africa/Nairobi when the key is configured. Set retention with `GOWNSEA_BACKUP_RETENTION_DAYS`. To mirror each encrypted archive to Laravel external storage, configure a private disk, then set `GOWNSEA_BACKUP_EXTERNAL_DISK` and optionally `GOWNSEA_BACKUP_EXTERNAL_PREFIX` (default `gownsea-backups`). The included `s3` disk uses the AWS-compatible S3 adapter and standard `AWS_*` environment values. `gownsea:restore <filename>` downloads an archive from that disk when the local copy is absent. Configure private access, object versioning, lifecycle retention, access logging and a separate account/region at the storage provider. Local disk alone is not disaster recovery; storage credentials and an isolated restore drill are still required before launch.

Restore only during an approved recovery window after testing the selected backup in an isolated environment. The command takes a pre-restore backup, enters maintenance mode, restores the database and private files, then brings the app up on success. Example: `php artisan gownsea:restore gownsea-YYYYMMDD-HHMMSS-XXXXXXXX.gwbak`; use `--force` for a non-interactive operator run. Verify key records, payment/deposit/refund reconciliation, file access, queue health and login before reopening traffic. If restore fails, the app stays in maintenance mode for operator review. Define RPO/RTO and routinely test recovery into a separate environment; a local archive creation check is not a restore drill.

## Integrations

Onfon SMS uses a database outbox, template-based messages, customer opt-out, idempotency and the queue worker. Set `ONFON_SMS_CLIENT_ID`, `ONFON_SMS_API_KEY`, `ONFON_SMS_ACCESS_KEY`, and `ONFON_SMS_SENDER_ID` from rotated provider credentials. Never copy credentials from the checked-in PDF into configuration: treat those values as exposed and rotate them with Onfon before enabling live sends. Run a real delivery only after a controlled sandbox/test-recipient review, sender ID approval and queue-worker setup.

Daraja STK is disabled by default. Configure `DARAJA_ENABLED=true`, `DARAJA_ENVIRONMENT=sandbox` (use `production` only after Safaricom onboarding), the consumer key/secret, shortcode, passkey, transaction type and a random callback token of at least 32 characters. The callback endpoint must be publicly reachable over HTTPS in production. Only callback-confirmed payments enter the receipt ledger; callback replays are idempotent, and amount/phone/receipt mismatches enter manual review. Network timeouts also remain in review because the provider may have accepted the prompt. Reconcile uncertain requests with Safaricom before retrying. Test prompts and callback delivery against Safaricom sandbox before production enablement.

Both integrations are disabled or inert unless their required settings are present. Provider credentials are not configured in this repository. Do not use the local provider mocks as evidence of a live provider approval or end-to-end delivery.

KRA eTIMS uses the approved OSCU/VSCU system-to-system route. Settings hold the signed tax category mappings, KRA branch/device/operator information, receipt/payment codes and go-live date. Set `ETIMS_ENABLED=true` and `ETIMS_VSCU_ENDPOINT` only after taxpayer onboarding, bridge initialization and certification. The bridge URL is deployment-only and accepts HTTPS or a local/private HTTP VSCU host. Accepted receipt metadata is encrypted in the outbox and shown on invoice/credit-note PDFs. A timeout or incomplete bridge response enters manual review and is never automatically retried; reconcile with KRA first. Historical invoices before the approved go-live date remain in cutover review and are not submitted automatically. See the implementation progress record for the KRA specification links and outstanding provider gates.
